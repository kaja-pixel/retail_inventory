1. Business Scenario

A retail shop currently manages its products, stock quantities, prices, employees, and sales-related inventory activities manually using notebooks and spreadsheets.

This creates several problems:

- Duplicate product records.
- Incorrect stock quantities.
- Difficulty tracking inventory changes.
- Unauthorized access to sensitive information.
- No proper employee role management.
- Difficulty identifying low-stock products.
- No centralized notification system.
- No reliable record of who created, updated, or deleted products.
- Time-consuming inventory reports.

Your task is to develop a **Retail Inventory & Stock Management Web Application** that solves these problems through a secure, role-based, full-stack application.

You must start the project from scratch, design the database, implement the backend API, build the frontend, integrate authentication, and test the complete application.

4. User Roles and Permissions

The application must support the following roles.

4.1 Super Admin

The Super Admin has the highest level of access.

Permissions:

- Access the system dashboard.
- Create, view, update, and deactivate user accounts.
- Assign roles to users.
- View all products and inventory records.
- Add, edit, and delete products.
- View all notifications.
- Access audit logs.
- View inventory reports.
- Configure low-stock thresholds.
- Review user activity.

The Super Admin role must not be assignable by an ordinary user during registration.

4.2 Admin / Inventory Manager

Permissions:

- Access the inventory dashboard.
- Add, view, and edit products.
- Manage stock quantities through authorized stock adjustments.
- View low-stock alerts.
- View product-related notifications.
- Search and filter products.
- View inventory reports.
- View relevant inventory activity logs.

An Admin must not be able to promote themselves to Super Admin or manage protected Super Admin privileges.

4.3 Staff / Employee

Permissions:

- Log in to the system.
- View products and stock quantities.
- Search products by name or SKU.
- View low-stock alerts relevant to their work.
- View their own notifications.
- Perform only the inventory operations explicitly authorized for Staff.

Staff must not be able to manage user roles, access protected audit logs, or perform unauthorized product deletion.

Role Enforcement Requirements

- Every protected API endpoint must verify the user's identity.
- The backend must check permissions for each protected operation.
- Hiding buttons in React is not sufficient security.
- Unauthorized requests must be rejected by the backend.
- Users must not be able to change their role by editing a request.
- A regular user must never be able to grant themselves Admin or Super Admin privileges.

5. Authentication and Account Management

Implement a complete authentication module.

5.1 User Registration

Create a registration page with:

- Full Name
- Email Address
- Password
- Confirm Password

Requirements:

- Validate all required fields.
- Validate email format.
- Enforce an appropriate password policy.
- Confirm that the password and confirmation match.
- Prevent duplicate email registrations.
- Hash passwords before saving them.
- Never store plaintext passwords.
- Assign new users the default `STAFF` role.
- Do not allow users to select their own privileged role during registration.
- Display clear success and error messages.

5.2 Email and Password Login

Create a login page with:

- Email Address
- Password
- Remember Me, if implemented securely
- Forgot Password link
- Sign in with Google button

Requirements:

- Verify credentials on the backend.
- Reject invalid credentials without revealing whether a specific account exists.
- Create an authenticated session or issue a secure token.
- Redirect users according to their role and permissions.
- Display a clear message when login fails.
- Implement logout.
- Invalidate the session or refresh-token mechanism appropriately on logout.

5.3 Google / Gmail Authentication

Integrate **Google Sign-In using Google OAuth 2.0 / OpenID Connect**.

Requirements:

- Display a “Continue with Google” button.
- Allow users to authenticate using their Google account.
- Verify the Google identity token on the backend using a trusted Google verification library.
- Verify the token's audience and relevant claims.
- Use the verified Google identity to identify the account.
- Create a new account when permitted by the application's registration policy.
- Assign new Google-authenticated users the default `STAFF` role.
- Prevent users from obtaining elevated privileges through Google Sign-In.
- Handle cancelled authentication and failed verification.
- Store client IDs and secrets in environment variables.
- Never trust a user-provided email address without verifying the Google identity.

**Important:** Google Sign-In is an identity authentication feature. It does not mean the application should request unrestricted access to the user's Gmail inbox.

5.4 Forgot Password and Reset Password

Implement a secure password recovery workflow.

Requirements:

- Allow a user to request a password reset.
- Generate a cryptographically secure, single-use, time-limited reset token.
- Send a reset link through an email provider or an approved development email service.
- Verify the token before allowing a password change.
- Invalidate the token after successful use.
- Never email the user's existing password.
- Do not expose whether an email address is registered.

If email delivery cannot be configured during development, implement the reset-token workflow safely and document the email integration limitation. Do not expose production reset tokens in API responses.

5.5 User Profile

Create a profile page where users can:

- View their name and email.
- View their assigned role.
- Update permitted profile fields.
- Change their password when using password-based authentication.
- View their account status.

Users must not be able to change their own role or verification status.

#Required Notification Types
1. Low-stock notification.
2. Out-of-stock notification.
3. New product created notification.
4. Product information updated notification.
5. Stock quantity adjusted notification.
6. Important account or administrative notification.

#Notification Features
- Display a notification bell in the navigation bar.
- Display the unread notification count.
- Show the notification list.
- Mark a notification as read.
- Mark all notifications as read.
- Display the notification creation time.
- Show a suitable message when there are no notifications.
- Allow users to access only the notifications they are authorized to see.

# Low-Stock Alert Logic
When a product's stock quantity becomes less than or equal to its configured low-stock threshold, the system must identify it as low stock.

When the stock reaches zero, display it as out of stock.

Avoid generating duplicate notifications for every page refresh. Design an appropriate strategy for notification creation and status tracking.

# Notification Delivery
Required:

- Persistent in-app notifications stored in PostgreSQL.

Advanced option:

- Real-time notification updates using WebSockets or Server-Sent Events.
- Email alerts for low-stock products or important administrative events.

Real-time delivery and email notifications may be treated as advanced extensions if the core application is not yet complete.

# DAY 5 – AUTOMATED TESTING, CI PIPELINE & INCIDENT DEBUGGING

## Project: Retail Inventory & Stock Management Web Application

### 1. Business Scenario

Your development team has been developing a Retail Inventory & Stock Management Web Application to replace the manual product, stock, and inventory management processes used by retail shops.

The application includes the following features:

- User registration and login.
- Google Sign-In authentication.
- Role-Based Access Control (Super Admin, Admin, and Staff).
- Product management (Create, Read, Update, Delete).
- Inventory and stock adjustments.
- Product search, filtering, sorting, and pagination.
- Low-stock and out-of-stock notifications.
- Dashboard analytics.
- User management.
- Inventory transaction history.
- Audit logs.
- User profile management.

During the latest development cycle, the team identified several issues:

- Some API endpoints return unexpected responses when invalid data is submitted.
- Product creation and updating may fail under certain conditions.
- Inventory adjustments may produce incorrect stock quantities if validation is insufficient.
- Unauthorized users may attempt to access restricted API endpoints.
- Low-stock notifications may be generated repeatedly for the same product.
- There is no proper automated testing process to verify existing features after code changes.
- Developers sometimes run tests using the development database, which may accidentally affect existing records.
- When a developer pushes code to GitHub, there is no automated process to verify whether the application is still working correctly.
- When an API request fails, identifying the exact request and tracing the error takes additional time.
- A previously fixed issue may occur again when new changes are introduced.

Your team has decided to improve the application's reliability by implementing automated testing, a separate testing database, a Continuous Integration (CI) pipeline, and structured request logging.

You are assigned to complete these improvements without breaking the existing Retail Inventory & Stock Management application.

## TASK 04 – Configure a Separate Testing Database

Your application must use a separate PostgreSQL database for automated testing.

Implement the following:

1. Create a dedicated testing database.
2. Configure environment variables for the testing database.
3. Ensure automated tests connect to the testing database.
4. Keep development and testing database configurations separate.
5. Prepare the testing database before running tests.
6. Clean up test data where necessary.
7. Ensure tests can run repeatedly without depending on previous test data.
8. Use database transactions or appropriate cleanup strategies where necessary.

Recommended database names:

Development database:
`skillforge_inventory_db`

Testing database:
`skillforge_inventory_test_db`

Example environment configuration:

```env
DATABASE_URL=postgresql://USER:PASSWORD@localhost:5432/skillforge_inventory_db

TEST_DATABASE_URL=postgresql://USER:PASSWORD@localhost:5432/skillforge_inventory_test_db
```

IMPORTANT:

- Never run destructive test operations against the development or production database.
- Never commit database passwords or secret keys to GitHub.
- Use environment variables for sensitive configurations.
- Verify which database is connected before executing destructive test operations.
- Ensure automated testing cannot accidentally connect to the production database.

## TASK 05 – Implement GitHub Actions CI Pipeline

Configure GitHub Actions to automatically execute the project's checks whenever code is pushed or a Pull Request is created.

The CI pipeline must:

1. Check out the latest source code.
2. Set up the required Node.js runtime environment.
3. Install frontend and backend dependencies.
4. Configure the testing environment.
5. Set up PostgreSQL for testing where required.
6. Prepare the testing database and schema.
7. Execute backend automated tests.
8. Execute frontend tests or build checks where available.
9. Report whether the workflow passed or failed.

Expected behaviour:

- If all tests pass, the workflow should complete successfully.
- If any test fails, the workflow should report failure.
- A Pull Request must clearly show the CI result.
- Developers must be able to identify which step failed.
- CI must never use the development or production database.

Create the GitHub Actions workflow file:

`.github/workflows/ci.yml`

Do not disable failing tests or hide errors just to make the workflow pass.

## TASK 06 – Implement Request ID and Structured Logging

The development team needs a better way to identify and investigate API failures.

Implement request tracking and structured logging in the backend.

Your implementation must:

1. Generate a unique Request ID for every incoming API request.
2. Include the Request ID in API response headers.
3. Include the Request ID in relevant application logs.
4. Record important request information.
5. Record API errors with useful debugging information.
6. Include timestamps and appropriate log levels.
7. Record the HTTP method, endpoint, status code, and response duration where appropriate.
8. Avoid logging passwords, authentication tokens, database credentials, or other sensitive information.

Example response header:

```http
X-Request-ID: req-a8f21c9d
```

Example structured log:

```json
{
  "timestamp": "2026-11-19T10:30:00.000Z",
  "level": "error",
  "requestId": "req-a8f21c9d",
  "method": "GET",
  "endpoint": "/api/products/999",
  "statusCode": 404,
  "message": "Product not found"
}
```

Recommended logging libraries:

- Winston
- Pino

You may use an appropriate logging library based on the existing backend architecture.

## TASK 07 – Incident Investigation and Regression Testing

Your mentor will provide an API failure scenario during the task review.

The incident may involve any existing module of the Retail Inventory & Stock Management application.

Possible incident examples:

- Product creation fails when a duplicate SKU is submitted.
- Inventory adjustment produces an incorrect stock quantity.
- Staff users can access an Admin-only API.
- Product filtering returns incorrect results.
- Low-stock notifications are generated repeatedly.
- Dashboard statistics do not match the actual database records.
- Product updates return unexpected server errors.

When you receive the incident:

1. Reproduce the reported issue.
2. Identify the affected API endpoint.
3. Capture the Request ID from the API response.
4. Use the Request ID to locate the relevant application logs.
5. Investigate the root cause.
6. Fix the identified issue.
7. Write an automated regression test for the issue.
8. Run the complete automated test suite again.
9. Verify that previously working features are not affected.

You must explain:

- What caused the issue?
- How did you identify the root cause?
- What changes did you make?
- How does your regression test prevent the issue from returning?

Do not randomly modify code without identifying the root cause.
